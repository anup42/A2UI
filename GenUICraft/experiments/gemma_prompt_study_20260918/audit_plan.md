# Independent audit plan — Gemma E2B prompt study

Read-only source review, 2026-09-18. This plan records controls and acceptance checks; it contains no new device measurements. No code, build, installation, or device operation was performed for this audit.

## Controls that affect validity

- Run every candidate, including the explicit baseline, with `provider=gemma`, `accelerator=GPU`, `mtp=true`, `sourceBindings=true`, `temperature=0.0`, the same explicit `thinkingBudget`, and the same time limit. Keep the model, AAR, APK/test APK, runtime, corpus, and converter revision fixed. The current default is thinking enabled with a 1,024-token budget and an 8,192-token output limit; record effective values rather than relying on omitted defaults.
- **Custom prompts require `sourceBindings=true`.** `promptPath` calls `GenUiConverter.withPrompt`, whose binding flag defaults to false. A successful direct-copy conversion is a different experiment. On accepted cases, check both the GPU+MTP runtime identity and the exact-source-bindings warning, as well as the actual launch arguments. The built-in `run_config.json` does not currently record prompt path/hash or the binding flag, so the host provenance manifest must do so.
- Hash each immutable prompt before and after its run. The copied baseline currently matches bundled `gemma.txt`: SHA-256 `154FF4D27D8E37B81279E7979C18B4FD90BBDD5135A4E124917712A85438535B`. Persist exact launch arguments, ordered case IDs, prompt/input lengths, runtime settings, binary/model/corpus hashes, and unique output directories. Never overwrite an earlier variant's artifacts.
- The converter supplies the root assignment and block element names. The source-binding contract accepts only typed content placement, exact once-only binding use, source order, and a restricted component/property set. Variants must not ask for invented summaries/titles, actions, unsupported charts, copied facts, split tables, or reordered blocks. Heading styling can be restored deterministically by the current binder; distinguish that SDK behavior from a model following the raw heading instruction.

## Fair screening and selection

1. Use the planned eight prompts on BXP-003/030/032/037 with `repairs=0`. These deliberately include all three previously repaired cases, so this is a development screen, not an unbiased accuracy estimate.
2. Keep case order equal across variants; randomize or counterbalance variant order and repeat the baseline at the end. **The `cases` argument filters corpus order; changing argument order does not reorder execution.** BXP-003 remains the first/cold case in this screen. The provider initializes lazily and reuses its engine within a run, so report first-in-run and subsequent-case timings separately.
3. Record pre/post thermal status, available sensor readings, battery/charging state, and run timing. Keep display/device conditions consistent; compare within a documented starting-temperature band when available. Battery temperature is a proxy, not a GPU-temperature measurement. A faster late run or slower hot run alone does not establish a prompt effect; use the repeated baseline to identify drift.
4. Confirm the best candidates on an additional fixed diverse subset, including weather (001), long road-trip cells (006), lodging (009), product comparison (011), numeric deposits (013), long privacy content (028), many headings (045), and long history content (048). Preserve this subset before inspecting results. Repeat close contenders because temperature zero does not guarantee identical GPU/MTP execution.
5. Select primarily by strict first-pass validity and preservation, then rendering/domain quality, then comparable latency. Run the selected frozen prompt on all 50 with `repairs=1`; report first-pass and repaired success separately. The full corpus has informed development, so describe it as this corpus's regression result, not unseen-input generalization.

The historical v7 run is context only: 47/50 first pass and 50/50 after repair. Its BXP-030/032/037 elapsed times (187,934/342,430/317,400 ms) include two attempts and cannot be compared to a one-attempt screen as a speed improvement. Use a fresh same-build, same-settings `repairs=0` baseline. Report paired per-case deltas and small-screen range/median; four cases do not support a meaningful p95 estimate. Include failed/time-limited cases and their elapsed time rather than computing a winning latency only from easy successes.

## Evidence validation

- Require exactly the planned unique case IDs, one terminal result per case, a completed instrumentation run, no stale output directories, and the expected raw attempt files. With repairs zero, accepted conversions must have `attempts=1` and only `attempt_1.txt`. A provider call that times out can produce no raw file and be reported with `attempts=0`; do not equate absent files with zero inference attempts.
- Separate conversion validity from rendering smoke status: the current benchmark's `success` also depends on screenshot/XML checks, while `render_failure` can still contain a valid compiled conversion. Classify syntax/binding/content failures, timeout/runtime failures, and rendering failures separately. Preserve rejected raw output and errors.
- Recompile saved Express and wire JSON, check their equivalent canonical content, and verify exact binding expansion/content integrity. Check original literal values, table dimensions/cell order, headings, lists, caveats, numeric values, citations, and URLs. Count source blocks via typed placement, not regex counts of raw `@source` text that could appear inside literal source content.
- `outputTokens` is an optional SDK decode-counter result; it is not proven to mean final Express tokens alone. Do not label `outputCharacters / elapsedMs` as token throughput or infer omitted token counts. Whole-app PSS includes the runtime/cache and is not model-only memory.
- Use fresh cache-cleared hierarchy captures and bounded replay for renderer evidence. Treat `renderer_replay` and `captured_model_revalidation` reports as zero-live-inference validation, never as additional successful model runs. A screenshot plus several text nodes is only a smoke check.

## Layout-independent domain and rendering audit

Match each output table to source/baseline using a fingerprint of its ordered columns and rows; ignore component IDs, property order, and container nesting. Compare content first, then retain a per-table record of `domain`, `preferredPresentation`, source table shape, heading treatment, and observed rendering route.

Use acceptable choices rather than an exact baseline layout oracle. BXP-003 contains train-service entity rows: schedule cards or a complete generic/comparison table can both be reasonable. BXP-030 and BXP-037 are feature matrices: a table is a strong default, and the audit should flag a domain-specific route that obscures the feature-to-entity relationship. BXP-032 is a terms/meaning/effect table: generic/comparison cards or a table are plausible. Unrelated weather/flight/booking semantics deserve review even when schema-valid. A blanket generic-table prompt may improve syntax while reducing useful domain treatment; report that tradeoff rather than declaring every changed layout a regression.

Automatically check reachable header/cell evidence, original units, all rows/columns, source-order headings, no blank/omitted blocks, and no renderer error. Inspect screenshots for changed or suspicious domain choices, long cells, feature matrices, and final columns. Accessibility text can expose a clipped value; column-observation checks are useful evidence but not proof of visual completeness. Require full content preservation and usable navigation, not pixel-identical screenshots.
