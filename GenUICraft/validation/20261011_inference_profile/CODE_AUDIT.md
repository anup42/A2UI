# E2B inference code audit — 2026-10-11

This is a source audit, not a new device measurement. The probe exercises the trained E2B v10 profile with GPU, corrected FP16, zero-temperature/no-thinking generation, and optional MTP, streaming previews, and provider reuse. It does not exercise the official E2B profile or an Activity. Sources: `GenUICraft/genuicraft/src/main/java/com/samsung/genuicraft/sdk/GenUiSession.kt:25-50`; `android/app/src/androidTest/java/com/samsung/genuicraft/InferenceBottleneckProbeTest.kt:36-45,93-121`.

## Timing boundaries

| Reported field | Actual interval and interpretation |
| --- | --- |
| `conversionWallMs` | Monotonic `elapsedRealtimeNanos` from just before observer construction through `session.convert` return (or exception). Includes session preparation, lazy native initialization if needed, prompt/prefill/decode, streaming callbacks, final compile/repair, and preview worker stop/final publication. Device-state reads and artifact writes are outside it. The test wrapper deliberately makes the session's `finishGenerationMetrics` hook a no-op. Sources: probe `:211-245`; `GenUiSession.kt:127-168`. |
| `providerTotalMs` | Sum of provider-attempt wall intervals. Normally one trained-profile attempt. Includes lazy engine initialization, generation, and synchronous native/SDK callback work; it is nested inside `conversionWallMs`, not additive. `conversionMinusProviderMsApprox` also contains session preparation, observer setup, scheduling, compile/repair, and preview completion; it is not a clean “repair time.” Sources: probe `:263-278`; `GenUiStreamingProvider.kt:25-40`; `GenUiTrainedConverter.kt:53-79`. |
| `conversionElapsedMs` | Trained converter's own `System.nanoTime` interval, beginning after session preparation and ending after compile/repair. It excludes session finalization and preview completion. Sources: `GenUiTrainedConverter.kt:53-79`; `GenUiSession.kt:153-168`. |
| Native `engineInitializationSeconds`, TTFT, prefill/decode rates | Engine initialization wall time surrounds model validation and native engine creation on the first use of this provider. Native initialization *phase sum* can overlap and must not be added to wall time. TTFT includes prefill, so it must not be added to prefill; prefill/decode durations inferred from tokens ÷ rates are approximate. Sources: `Gemma4Runtime.kt:96-105,260-325`; `Api.kt:63-80`; `android/app/src/main/java/com/samsung/genuicraft/ui/GenerationMetricsUi.kt:28-55`. |
| `finishMetricsMs`, `closeAndAwaitMs` | Sequential teardown intervals outside `conversionWallMs`. With MTP and metrics enabled, `finishGenerationMetrics` closes the native engine to obtain acceptance data, then reads bounded process logcat; the separate close call follows. With MTP off, the finish hook does not close the engine, so closure falls in `closeAndAwaitMs`. Sources: probe `:308-334`; `Gemma4Runtime.kt:197-225,506-532`; `GenUiSession.kt:171-181`. |

The cold arm creates a provider per case; its `providerConstructionMs` covers only `newProvider()`, while native engine initialization occurs on the first generation. Session construction and the artifact writes inserted between conversion and teardown are not timed as one uninterrupted request. Thus `conversionWallMs + finishMetricsMs + closeAndAwaitMs + providerConstructionMs` is an **analytical sum of measured intervals**, not a directly observed tap-to-ready wall time. In the reuse arm one finalization/close belongs to the whole batch, not each request. Sources: probe `:125-173,244-305,308-334`; `Gemma4Runtime.kt:96-105`.

## Probe validity and interpretation

The reuse arm performs one excluded warmup, retains the same session/provider, and defers native metrics finalization until the end; this is the correct mechanism for measuring warm requests with MTP enabled. The native `engineInitializedForRequest` flag is saved per result. However `runComplete` checks only conversion success and teardown MTP state: it does not require warmup `engineInitializedForRequest == true`, reuse results `== false`, or cold-arm results `== true`. Treat reuse/cold as *requested modes* until those flags are verified and exclude null or mixed cases from warm/cold comparisons. Sources: probe `:125-185,263-293`; `Api.kt:75-78`; `Gemma4Runtime.kt:96-105,197-225`.

`firstPartialCallbackMs` measures the first nonempty raw callback; `firstPreviewCallbackMs` and `firstReadyPreviewCallbackMs` measure SDK provisional-snapshot publication. There is no Activity, Compose frame, or visible-pixel measurement in this probe. The preview compiler is throttled/coalesced on a separate worker and can overlap decoding. `callbackBodyWorkMs` sums only this probe observer's atomic counter/timestamp work; it excludes native/JNI callback dispatch, cumulative-text copying, repetition scanning, SDK snapshot capture, preview compilation, and UI work. Do not add or subtract it as a separate wall phase or call it total callback overhead. Sources: probe `:36-45,211-232,285-291`; `GenUiPreviewCoordinator.kt:12-57,85-100`; `Gemma4Streaming.kt:29-51`; `GenUiOutputRepetitionGuard.kt:20-29`; `GenUiStreamingProvider.kt:25-40`.

The probe's `streaming` switch disables **preview compilation/publication**, not the raw native asynchronous stream or the observer's partial-text callbacks. Streaming on/off therefore estimates the incremental preview path under otherwise comparable requests; it does not isolate all streaming callback work. Sources: `GenUiSession.kt:122-145`; `Gemma4Runtime.kt:157-164`; probe `:214-240`.

The cooldown waits a minimum delay and then for Android thermal status `NONE`, but a timeout/unavailable status is recorded and nonfatal; `runComplete` does not test `thermalReady`. Only before/after battery temperature and coarse thermal status are sampled, not within-run GPU clocks or throttling. The case order is fixed across repeats. For rate comparisons, report per-run thermal state, exclude or separately label cooldown timeouts, compare matching prompts/output-token counts, and counterbalance mode order. Sources: probe `:70-75,139-165,174-185,336-381`.

## Ranked code diagnosis and follow-ups

1. **Confirmed lifecycle cost:** the SDK demo defaults token metrics and MTP on (subject to selected-model support), and `GenUiSession.convert` calls finalization before returning. MTP finalization closes the engine, so retaining the same provider does **not** make successive default SDK-page requests warm. The main trained Stage 3 bridge creates and closes a provider/session for each invocation. First optimization to evaluate: explicitly retain a trained provider/engine across requests and defer MTP acceptance finalization until that engine is actually retired; compare against cold behavior with identical settings. Sources: `android/app/src/main/java/com/samsung/genuicraft/ui/GenUiSdkDemoActivity.kt:63,91,105-106,652-663`; `GenUiSdkDemoViewModel.kt:141-174,250-285`; `GenUiSession.kt:153-168`; `Gemma4Runtime.kt:197-225`; `android/app/src/main/java/com/samsung/genuicraft/pipeline/TrainedStage3Bridge.kt:135-144,176-209`.
2. **Measured partition needed:** first-request initialization includes corrected-FP16 model verification and native engine creation. The model SHA-256 validation is cached by file identity within a process, so it can affect the first cold request but should not be assumed to recur for every same-process provider. Use `engineInitializedForRequest`, engine-init wall time, and process identity to separate these costs; do not mistake native phase sum for wall time. Sources: `Gemma4Runtime.kt:96-105,260-325`; `GpuFp16Correction.kt:74-88`; `Api.kt:75-80`.
3. **Likely workload cost, magnitude unproved here:** the pinned three-message trained prompt and generated-token count affect prefill and decode. Compare native input/output tokens, prefill/decode rates, and TTFT at matched prompt and output lengths before changing prompt or output limits; the trained prompt checksum is a checkpoint contract and cannot be shortened casually. Sources: `GenUiTrainedConverter.kt:167-193`; `GenUiSession.kt:25-50`; `Api.kt:63-74`.
4. **Possible CPU overhead, not established as dominant:** each native delta copies the full cumulative response and rescans it for repetition; the SDK also captures cumulative snapshots and may run preview compilation on a coalesced worker. Compare preview on/off in a warmed, thermally matched arm for the incremental preview cost; instrument the native callback/guard separately if a reproducible gap remains. Sources: `Gemma4Streaming.kt:29-51`; `GenUiOutputRepetitionGuard.kt:20-29`; `GenUiStreamingProvider.kt:25-40`; `GenUiPreviewCoordinator.kt:20-57`.

For real SDK-page latency, measure button-to-first-visible-frame and button-to-ready separately from this headless probe. The SDK page posts raw updates to main and throttles displayed text to 75 ms; its completion occurs only after the session's MTP finalization. Sources: `GenUiSdkDemoViewModel.kt:189-218,250-285,329-337`; `GenUiSession.kt:153-168`.
