# Resource trace analysis (finalized 2026-10-11 profile)

This is a read-only correlation of saved profiling artifacts for SM-F776U (`R3GL203AKSF`) and SM-F971B Fold8 (`R37L20059SY`). The finalized `summary.json` contains eight complete arms, 36 saved measured requests, and six excluded startup warmups. Only three measured requests meet the strict cooled criterion, so cross-arm differences below are descriptive. It uses each arm's `telemetry.jsonl`, each device's `resource_samples.jsonl`, the completed `device/*/result.json` files, and `REPORT.md`.

## Timing and metric boundaries

For each result, I matched samples whose `hostEpochMs` falls between `deviceBefore.epochMs` and `deviceAfter.epochMs`; the latter bracket the conversion but include small device-state-read margins (`android/app/src/androidTest/java/com/samsung/genuicraft/InferenceBottleneckProbeTest.kt:211-245`). Host and device timestamps agree to about a second in these captures, not to a kernel-level timestamp. Arm GPU telemetry is approximately every 3.1 seconds; resource sampling is approximately every 5.3 seconds. A 4–7 second request therefore has only 1–2 samples or none. Min/median/max below are **sample statistics**, not time-weighted averages.

The telemetry `raw` fields, in order, are device epoch seconds, `/sys/class/kgsl/kgsl-3d0/clock_mhz`, `gpu_busy_percentage`, `max_clock_mhz`, and `temp` (the file's first records and the matching ADB command in `R3GL203AKSF/diagnostics_running/20261011_084953/logcat_filtered.txt:1-2`). The temperature values are reported in thousandths of a degree C. Android `Thermal Status` and HAL skin temperature follow. These sysfs reads show sampled frequency, busy, and a **reported maximum available at the sampled instant**; `max_clock_mhz` is not an immutable hardware peak or a diagnosis of what set the limit. They do not expose per-kernel utilization, GPU power, memory traffic, or effective DRAM bandwidth. `resource_samples.jsonl` supplies `/proc/meminfo`, CPU and memory PSI 10-second averages, two sampled CPU-policy frequencies, and `ps` RSS. CPU frequencies are not CPU utilization; PSI is a system-level stall signal, not a model-specific allocation or GPU-bandwidth counter.

Both resource streams start around 08:49:41 IST, after the cold baseline requests. They have a large collection gap, then resume through the final streaming arms: Fold8 **09:05:53.733–09:16:58.981** (665.2 s) and F776U **09:05:13.703–09:16:58.525** (704.8 s). Arm GPU telemetry continued across the gaps. The Fold8 MTP-off BXP-031 requests at about 09:07 and 09:13 have no CPU/memory/PSI samples despite having GPU samples. Late streaming requests have sparse resource samples after collection resumes. Nearby idle or different-request polls cannot fill these gaps.

## What these resources narrow down

The F776U MTP-off BXP-031 slowdown does **not** show contemporaneous device-wide memory pressure: 10 and 9 resource polls inside the two requests report 4.63–4.80 GiB available and memory PSI avg10 at zero. The GPU is sampled busy near 90% while the **reported maximum available clock** is low. That makes the ceiling and the extra sequential work without MTP practical issues to investigate, but the samples cannot separate their individual contributions. Both devices' BXP-001 cases show a mode-associated decode-rate difference when the compared requests sampled 1300 MHz, so a BXP-031 clock drop cannot explain the entire MTP-on/off difference.

Fold8's second warm MTP-on BXP-031 degraded relative to its first with a 461 MHz reported GPU maximum, Android status 4, and rising memory/CPU PSI together. That pressure reading does not establish which process stalled or whether the model exceeded physical RAM; it is also not evidence of GPU memory-bandwidth saturation. Both later Fold8 MTP-off BXP-031 requests repeat the 461 MHz ceiling and reach status 4, but have **no** contemporaneous CPU/memory samples during the collection gap. The completed streaming arms resume mostly 1300 MHz GPU samples with sparse late resource polls; coarse status 3 alone did not imply a sampled clock reduction on Fold8.

Current GPU clock and reported maximum often move together during the observed drops, but this is a correlation, not a clock-versus-throughput scaling law. `max_clock_mhz` changes inside requests, individual token/kernel boundaries are unsampled, and mode, output length/content, arm order, cooldown timeouts, and thermal/system state differ. Fold8 BXP-031 MTP-on #1→#2 keeps output count equal but changes clock, thermal state, and memory/CPU pressure together, so none is isolated as the cause. App RSS and `MemAvailable` do not measure the model's GPU-resident working set or GPU memory traffic.

These traces support a narrow root-cause account: cold requests spend material time in engine initialization (request-level wall metric); warm long generations spend material time in decode; MTP-off runs are slower at the native decode-rate level; and sustained reported GPU clock ceilings coincide with the worst long requests. They do **not** identify an executing OpenCL kernel, measure decoder FLOPs/GFLOPS, prove GPU compute or memory-bandwidth saturation, or establish whether thermal, power, or governor policy set the clock limit. Only 3/36 measured requests are strictly cooled, and the warm streaming pairs remain descriptive in `REPORT.md`. The native graph and profiling limits are detailed in `NATIVE_ANALYSIS.md`.
