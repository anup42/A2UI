# FP16 quantize/dequantize precision boundary

The captured original GPU kernel [program_00013_qdq_original.cl](evidence/kernels/program_00013_qdq_original.cl) declares `half4 clamped_value`, `half4 quantized_value`, and `half4 dequantized_value` (lines 78–82). In its quantization step, half subtraction and multiplication occur **before** `round()`. Unlike a smooth half error, a value that crosses a half-integer threshold selects an adjacent quantization bin. The same kernel stores its scalar grid coefficients in `shared_half4_0`. This is generated fused quantize/dequantize arithmetic for model `QUANTIZE`/`DEQUANTIZE` operations; the inspected model has no standalone `FAKE_QUANT` operator.

[qdq_numerical.json](qdq_numerical.json) gives a reproducible threshold example using the SHA-verified model's decode `QUANTIZE` op 2 scale and a **constructed**, half-representable input. With the captured half-rounded coefficients, half arithmetic reaches exactly 20.5 and OpenCL `round()` selects bin 21; float arithmetic on the same half coefficients reaches 20.49462890625 and selects bin 20. This proves the arithmetic mechanism and isolates intermediate precision from coefficient precision. It does **not** claim that this exact activation occurred on the device. Additional examples are in the temporary audit `quant_grid_compare.json`.

The controlled device result supplies the causal test: correcting only the RoPE lookup path improved the BXP-003 570-token fixed-target score from original FP16 **-226.155121** to **-40.630646**. Promoting fused Q/DQ intermediates to float alongside corrected RoPE improved it to **-22.991875**, compared with original FP32 **-26.047764**. The score uses the identical target tokens and weights. RoPE + float Q/DQ produced one of two strict-valid raw generations, so this is a substantial numerical correction rather than a release-quality guarantee. The [full A/B report](REPORT.md) records prompts, controls, raw outputs, and limitations. The float-GEMV experiment is not required to close this fixed-target gap.

## Pinned source correction proposal

The [LiteRT 2.2.0 Q/DQ implementation](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/tflite/delegates/gpu/common/tasks/quantize_and_dequantize.cc#L23-L50) selects `AddHalf` min/max/scale whenever precision is F16 or F32_F16, emits `FLT4` math, and clips tiny scales in that branch. Therefore the mixed matrix-accumulation precision enum does not preserve this quantization grid. The [seven-file source patch](evidence/upstream/litert_v2.2.0_qdq_fp32.patch) instead retains model coefficients as float, converts each input vector to float for clamp/round/dequantize, and converts to the declared output tensor type afterward. It carries `GpuInfo` through the selector so [backend-aware conversion helpers](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/tflite/delegates/gpu/common/task/util.h#L43-L56) generate OpenCL, Metal, or GLSL expressions. It adds two direct deps to the [pinned Bazel Q/DQ rule](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/tflite/delegates/gpu/common/tasks/BUILD#L761-L787): `common:gpu_info` and `common/task:util`. The existing Abseil strings dependency covers `absl::Substitute`. Four direct factory calls in the [Q/DQ test utility](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/tflite/delegates/gpu/common/tasks/quantize_and_dequantize_test_util.cc#L23-L149) now pass its existing `env->GetGpuInfo()`.

Run [the apply helper](../../tools/native_gpu_probe/apply_litert_qdq_patch.py) against a clean pinned `v2.2.0` checkout. It defaults to a dry run; `--apply` is explicit. Against a local seven-file snapshot of pinned upstream source, the helper reported all seven `Checking patch` entries; application succeeded; all seven resulting files matched the proposed source texts line-for-line. This is **source-application evidence only**. No native runtime was built from this patch, and the optimized `ml_drift` path in the shipped binary may require a corresponding fix. The diagnostic source-hook A/B did not restore original float coefficients, so its exact result cannot be assigned to this unbuilt patch.

A native validation should first compile the patched Q/DQ task and existing Q/DQ test utility with Bazel strict deps, then inspect generated code and run bin-boundary cases under F16, F32_F16, and F32 on each intended backend. Include a scale below binary16's smallest normal value, a half-integer threshold with model-like INT8 scale, and a fused FC→Q/DQ case to ensure conversion occurs before quantization. Finally capture the actual replacement kernels and compare fixed-target scores, raw BXP and Bixby50 outputs, timing, and MTP modes on both target devices before changing the app's FP32 production setting.
